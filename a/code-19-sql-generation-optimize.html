SQL 生成 优化：EXPLAIN 与索引实战

编程助手·更新于 2026-11-15·SQL 生成 优化, 慢查询 SQL 优化, EXPLAIN 执行计划, 索引建议, 慢查询 SQL 优化, EXPLAIN 执行计划 怎么看

接了个电商后台的报表需求，AI 十秒写出能跑的 SQL，结果上线后每天早上八点数据库 CPU 打满，一条查询跑 8.6 秒。把慢日志、表结构和 EXPLAIN 一起喂给模型重新问，SQL 从 8.6 秒压到 90 毫秒。SQL 生成 优化 这件事，AI 能把语法写对，但执行计划得自己看懂再让它改。

先让 AI 把 SQL 写对

我的提问模板固定四段：表结构、索引现状、业务语义、输出要求。表结构直接粘 SHOW CREATE TABLE，索引贴 SHOW INDEX FROM 的结果，业务语义写清一个订单一行还是按商品行，输出要求限死一条 SQL 加注释。AI 写之前我会先让它复述表关系和过滤条件，复述错说明提示词有歧义，这一步能拦掉一半返工。坑一：不写清楚状态字段的枚举，模型会拿 status = '已支付' 去比 tinyint，隐式转换让索引直接失效。坑二：时间范围用 DATE(created_at) 包了一层函数，走不了索引，改写成 created_at >= '2025-11-01' 才行。这两条我固定写进提示词，AI 出稿后先自查一遍。

EXPLAIN 读三列就够

慢查询 12,400,000 行的订单表，原 SQL 的 EXPLAIN 里 type 是 ALL，rows 一千两百多万，filtered 只有 1%，Extra 写着 Using filesort。诊断按顺序看：type 是不是 ALL 或 index，rows 是不是接近全表，Extra 有没有 Using temporary 和 filesort。三条全中就重建索引，只中一条先改 SQL。我加的联合索引是 (user_id, status, created_at)，key_len 14，type 从 ALL 变成 ref，rows 掉到 1,240，filesort 也消失，查询从 8.6 秒到 0.9 秒，再改写掉回表字段，稳定在 90 毫秒。慢查询 SQL 优化 的关键不是让 AI 猜索引，而是把 EXPLAIN 结果原样贴回去，让它逐列解释。EXPLAIN 的 rows 是估算值，和真实扫描行数差几倍很常见，MySQL 8.0 可以用 EXPLAIN ANALYZE 看实际耗时。

索引建议要自己验，别全信

AI 常见的三个错：建议的索引和已有索引前缀重复；给写多读少的表开五六个索引，写入慢了 40%；让你加索引解决深分页，其实该用延迟关联。我的验证流程是先在从库建索引，跑 EXPLAIN 对比 rows，再看执行计划是不是真走；统计信息旧的时候加完索引也不生效，先 ANALYZE TABLE。联合索引记最左前缀，区分度高的列放前面，范围查询列放最后，覆盖索引能省掉回表。EXPLAIN 执行计划 怎么看 我也教给模型：让它逐列解释并预测 rows 变化，我再对着实测核对，两边差两倍以上就重新分析。上线前再跑一次 EXPLAIN，确认没退化成 ALL，这条我写进发布检查单，每次发布前照单勾一遍。这套 SQL 生成 优化 的验收标准，比让模型说一句优化完成可靠得多。

总结

AI 写 SQL 快，但快不代表对：先把表结构和枚举喂清楚，再用 EXPLAIN 的 type、rows、Extra 三列定位，最后在从库验证索引。SQL 生成 优化 的闭环是生成、看计划、改索引、再测一遍，我的报表查询从 8.6 秒到 90 毫秒，靠的是每一步都有数字对照。慢查询 SQL 优化 别迷信建议，EXPLAIN 执行计划 怎么看 清楚了，模型给的答案才敢上线。
