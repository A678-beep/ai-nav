接口 文档 自动 生成：OpenAPI 落地三步

编程助手·更新于 2026-11-15·接口 文档 自动 生成, OpenAPI 3.0, springdoc, 注释 规范, OpenAPI 注释 规范, 接口 文档 CI 校验

接手一个 20 个微服务的项目，87 个接口，接口文档停在三月的版本，前端联调靠翻聊天记录。三周前开始把文档从代码里长出来：注释规范定死、生成器接进 CI、剩下的脏活交给 AI 补。两周后文档覆盖 92%，联调群里问接口的消息少了一大半。接口 文档 自动 生成 的关键不是工具，是把写文档的责任挪回写代码的人手上。

先定注释规范

我们统一 OpenAPI 3.0，Java 用 springdoc-openapi 2.5.0，Python 用 FastAPI 自带的 openapi，Go 用 swaggo。规则四条：每个方法必须有 summary，不超过 20 字，一句话说清干什么；description 写业务规则，比如金额单位是分、订单号 18 位；每个参数标 example 和是否必填；DTO 每个字段挂 @Schema，枚举值写全。这套 OpenAPI 注释 规范 定完，评审只花一个下午，比事后补文档省太多。坑有三个：springdoc 要把旧 @ApiModelProperty 换成 @Schema，混用会漏字段；中文描述里的全角冒号和引号会让渲染后的表格错位；只写成功返回等于没写，前端最想知道的是失败时返回什么。错误码单独建一张表挂到接口描述里，前端定位问题不用再问后端。

生成、校验、进 CI

接口 文档 自动 生成 的链路是：springdoc 起服务后访问 /v3/api-docs 拿 JSON，FastAPI 走 /openapi.json；CI 里一个 curl 把文件导出到仓库，Redoc 渲染成静态页。关键是校验：redocly lint 查规范，oasdiff 对比上一个版本，标出删字段、改类型这类破坏性变更，接口 文档 CI 校验 在合入前跑，避免上线才发现前端调不通。踩过的坑：springdoc 2.0 配 Spring Boot 3.2 会 404，升到 2.3 以上；泛型和继承的 DTO 容易生成空 schema，得手写 @Schema(implementation)；文档里别放内网地址和真实域名；谁手改了生成的 openapi.json，下次发布就被覆盖，只能改代码注释。Redoc 页面开搜索框，前端按关键字找接口比翻目录快。

AI 补剩下的注释

87 个接口里注释完整的不多，我用 Claude Code 读 Controller 和 DTO 批量补。提示词固定成：逐个方法补 @Operation、@Parameter 和 @Schema，方法签名和逻辑不许动，字段类型以 DTO 为准，example 用脱敏假数据。一次喂 8 个方法，多了它会漏；补完跑 mvn test 加 oasdiff 比对，50 个接口的注释两轮补齐，人工只改了 14 个。覆盖率从 35% 涨到 92%，原来估 3 人天，实际 4 小时收工。这套 接口 文档 自动 生成 链路里，AI 的坑很实在：它会编手机号、身份证当 example，要统一换成脱敏值；它假设字段必填，和 DTO 的 required 冲突；boolean 常被写成 string。所以别让它直接改整个文件，让它输出 JSON patch，人工合并更稳。补注释前先 git commit，AI 改坏了能一键回退，这步别省。

总结

现在这套流程跑得很顺：先定 OpenAPI 注释 规范，再让生成器从代码导出，最后用 AI 补齐历史接口。87 个接口、92% 覆盖、4 小时改完，这是接口 文档 自动 生成 带来的真实差距。接口文档不是写完就完，接口 文档 CI 校验 挡在合入前，改接口的人顺手就把文档改了。前端再问接口，我直接甩 Redoc 地址。
