API 设计 AI：命名、版本和错误码三步

编程助手·更新于 2026-11-15·API 设计 AI, RESTful 规范, 错误码 设计, 幂等 键, 接口 命名 规范, API 版本 兼容

去年给一个 B 端 SaaS 做开放平台，第一版 31 个接口交给 AI 出初稿，两天就被前端挑出 9 处不一致：/getOrderList 和 /order/list 并存，时间字段一个用时间戳一个用字符串，分页写死每页 10 条。返工一周，之后我把 API 设计 AI 的用法固定成三段：先写规范再出初稿、拿规则卡命名、单独一轮定版本和错误码。

先把规范喂进去，再让它出路径

第一步不是让它设计，是把 6 条硬规则写进提示词：资源用复数名词、动作交给 HTTP 方法、字段统一 snake_case、时间一律 ISO 8601 带时区、金额存整数分、ID 用字符串。接口 命名 规范 写在提示词里，比写在 wiki 上管用。第二步给实体和调用方：4 个资源（订单、支付、退款、发票）加 3 类调用方（App、H5、合作方），要求先出资源树再出路径，不写代码。第三步让它自查：同一资源有没有两条路径，路径里有没有动词。避坑一：模型默认爱生成 /getUserInfo、/createOrder 这种动词路径，不写死它一定给你；避坑二：一次让它设计 30 个接口，分页、幂等、错误响应会集体漏掉，按资源分批，一批 6 到 8 个。这一轮资源树从 18 个压到 14 个。

命名用规则压，先扫一遍同义冲突

广告位（文章中部）AdSense / 广告联盟代码插入点 · 建议 728×90 / 移动端 320×100

初稿出来，第二步按 接口 命名 规范 让 AI 扫同义冲突：上一版扫出 37 处，order_time 和 created_at 混用、user_id 和 buyer_id 指同一个东西、status 和 order_status 各写一套。规则先定死：路径层级不超过 2 层，orders/{id}/refunds 可以，再深就拆；命名不超过 3 个词；状态字段一律 X_status 并给枚举；分页参数在 page 加 size 和 cursor 里二选一。24 个增删改查接口最后压到 12 个，订单状态更新从 POST /orders/updateStatus 改成 PATCH /orders/{id}。这轮 API 设计 AI 的产出是一张 12 行接口表，横轴资源、纵轴动作，空格子说明该合。避坑三：PATCH 只传要改的字段，别像 PUT 一样整对象覆盖，前端漏字段会把数据写空；避坑四：布尔字段别用 is_delete，库里有 null 就变三态。

版本和错误码，先想好怎么退

版本不跟迭代走：/v1 写在路径里，加字段不升版本，删字段、改类型、收紧枚举才开 /v2；API 版本 兼容 期至少 6 个月，响应头提前 60 天带 Deprecation 和 Sunset。错误码一张表管全站：5 位数字，前 2 位标模块、后 3 位标错误，10021 代表订单模块库存不足；错误体固定 4 个字段 code、message、requestId、details；成功失败靠 HTTP 状态码区分，别在 200 里塞业务码，否则监控全打平。案例：退款接口 4 个状态，AI 初稿把 refund_status 和 order_status 合成一个字段，评审 90 分钟才拆开；创建退款还要幂等 键，同一个 Idempotency-Key 只处理一次。避坑五：时间戳统一毫秒，别混秒和毫秒；避坑六：别让模型决定版本策略，它只会说加个 v2，弃用公告和兼容期得人定。

总结

API 设计 AI 的顺序就三步：规范先写死、初稿按资源分批出、命名和版本各扫一轮。两个不要：不要拿它给的路径表直接交付，不要让模型替你定 API 版本 兼容 策略。31 个接口压到 24 个之后，前端联调从两天缩到半天，版本上线基本不再返工。
