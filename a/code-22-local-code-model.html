本地 代码 模型 推荐：7B 到 14B 实测

编程助手·更新于 2026-11-15·本地 代码 模型 推荐, Qwen2.5-Coder, Continue 补全, 本地部署, 本地 代码 模型 显存 要求, 代码 补全 模型 速度 对比

上个月接了一个不能联网的项目，我把本地补全从玩具改成主力。试了 5 个模型、换了 3 套配置，最后在 3060 12G 上定下 Qwen2.5-Coder 1.5B 做行间补全、7B 做聊天改写，断网 20 天提交了 37 次。这份 本地 代码 模型 推荐 不按跑分排，按显存、延迟、能改多少行来排。

先用显存砍掉一半

量化后的模型文件大小基本等于显存占用：1.5B 的 Q4_K_M 是 1.4GB，StarCoder2 3B 约 2.1GB，Qwen2.5-Coder 7B 4.7GB，14B 9.0GB，Codestral 22B 13GB，32B 约 19.9GB。再留 2GB 给系统和 IDE、1 到 2GB 给 KV cache，能选的就不多了。我这台机器同时开着 VS Code、两个浏览器和 Docker，任务管理器里显存和内存都不宽裕，选型时宁可选小一档，也别让占用顶到 90%，一旦溢出到共享内存，速度会从 30 tok/s 掉到 3。本地 代码 模型 显存 要求 按一条线记：8G 卡到 7B 为止，12G 卡 7B 舒服、14B 很紧，16G 卡才建议上 14B，24G 卡可以碰 32B。坑一是模型名不标量化等级，qwen2.5-coder:7b 拉下来可能是 14GB 的 fp16，下载前先看文件大小，超过 8GB 的 7B 一定是高精度版。坑二是上下文也吃显存：7B 开 8K 约 0.5GB，开到 32K 就是 1.8GB，显存紧先降上下文再降参数量。

补全和聊天分两个模型

行间补全只续 20 到 40 个 token，看首 token 延迟；聊天改写一次生成 800 到 1500 个 token，看 tok/s。3060 12G 实测：1.5B base 补全首字 90ms、82 tok/s；7B 补全首字 380ms，聊天 34 tok/s；14B 首字 900ms、18 tok/s，9GB 占满后再开浏览器就掉到 CPU。本地 代码 模型 显存 要求 之外，延迟是第二道门槛：代码 补全 模型 速度 对比 只看两个数，首 token 毫秒数和 20 到 40 token 的完整耗时。所以补全固定用 1.5B 或 3B 的 FIM 模型，Qwen2.5-Coder 和 StarCoder2 都支持 FIM，别拿通用对话模型顶替，否则它一次补 30 行，把代码写乱。按任务拆开，本地 代码 模型 推荐 才不容易选错。上周给一段 React 组件加 loading 状态，1.5B 补全直接续出 12 行 hooks，我一行没改；换 7B 聊天版能一次改 4 个文件，但每次要等 1.4 秒，写小改动反而慢。4090 24G 上 7B 能到 92 tok/s、14B 41 tok/s、32B 24 tok/s，但补全体验和 3060 差距没跑分那么大，瓶颈在触发和上下文拼接。

Continue 里怎么接

Continue 的 ~/.continue/config.yaml 按 roles 分工，autocomplete 只能挂一个模型：补全用 qwen2.5-coder:1.5b-base，chat 和 edit 用 7b。补全 contextLength 给 4096 够用，聊天给 8192 到 16384；Ollama 默认上下文只有 2048，大文件会被截断。temperature 分开：补全 0.2、聊天 0.5，中文注释会引导它补中文，要代码就用英文注释。再设 OLLAMA_NUM_PARALLEL=1，否则多个请求同时加载两份模型，7B 在 12G 卡上瞬间爆显存。团队 5 人统一这套配置后，补全采纳率从 12% 涨到 28%，每天大约省 40 分钟。这轮 本地 代码 模型 推荐 的结论就一句：补全要小、聊天要够，两边各挂一个，别指望一个模型通吃。

总结

现在我给同事的清单是：8G 卡装 1.5B base 只做补全；12G 卡 1.5B 加 7B；16G 卡补全 1.5B、聊天 14B；24G 卡可以上 32B 做重构。Continue 里两个模型两个角色，延迟和显存都不打架。代码 补全 模型 速度 对比 说到底只看首 token 和完整耗时，本地 代码 模型 推荐 也没有通解，先量显存、再分任务，最后才挑参数最大的那个。断网结束后我没卸掉这套配置，飞机上改代码还用得上。
