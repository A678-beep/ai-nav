代码 安全 审计：用 AI 扫 4 类漏洞

编程助手·更新于 2026-11-15·代码 安全 审计, SAST, Semgrep, 误报 处理, 仓库 安全 审计 流程, 安全 审计 误报 处理

团队四个人维护一个 4.2 万行的 Java 仓，上个月甲方做等保测评，要求两周内交一份代码 安全 审计 报告。全量人工审不现实，我排了一条流水线：Semgrep 打底、CodeQL 补数据流、大模型逐条判真伪、人只做最后定级。首轮 217 条候选，去重后 89 条，复核完 23 条真问题，其中 5 条高危，修复加回归测试用了 6 天。

先扫再判，范围切小

第一步切范围：按路由和权限模块切，一次 5 到 8 个文件、不超过 2000 行，controller、service、mapper、SQL 一起给，单给一个文件模型看不见数据流。第二步跑 Semgrep：semgrep --config=p/owasp-top-ten --severity=ERROR，4.2 万行 38 秒出 217 条，重点看命令注入、硬编码密钥、路径穿越、SSRF 四类。第三步开 CodeQL 的 security-extended 查询包补数据流，和 Semgrep 去重后剩 89 条。这套仓库 安全 审计 流程 的关键是别把 89 条直接丢进工单，先让人工抽查 10 条确认规则没跑偏，否则后面全是噪音。依赖漏洞单独用 Trivy 扫一遍，高危版本列成表附在报告最后一页。

提示词固定四段

广告位（文章中部）AdSense / 广告联盟代码插入点 · 建议 728×90 / 移动端 320×100

提示词按四段写：角色是有 10 年经验的 Java 安全审计员；范围只审下面 4 个文件，不猜没给的代码；要求每条给文件行号、CWE 编号、攻击者怎么构造请求、修复代码不超 3 行；输出 JSON 数组，字段固定为 severity、file、line、cwe、poc、fix。末尾必须加一句：数据流补不齐就标 need_more_context，不许编造。89 条分 9 批喂，每批 10 条，只让它回答真、假、待确认三选一。第一轮只给接口层和 service，前端代码不进上下文，跨端数据流靠人补。整仓一次贴进去会超过上下文，后半段文件直接被截断，漏检比误报更可怕，这也是代码 安全 审计 里最容易省错的一步。

误报处理与案例

AI 判真 31 条，人工留 23 条，误报率 74%。三类为主：MyBatis 的 #{} 已经参数化却被当成拼接、拦截器统一校验过的参数、测试代码里的假数据。处理方式是补上下文而不是关规则，把 mapper XML 和拦截器贴进去，12 条假阳性里 9 条能自动纠正。案例：一条订单查询接口，SAST 报 SQL 注入，AI 判真，人工看是 #{} 参数化，属误报；但同文件另一个 ${} 拼接的排序字段被它顺手标出来，那才是真洞，最后定为高危。23 条按 CVSS 3.1 定级，5 条高危、8 条中危，修完重跑 Semgrep 归零，补了 11 条回归测试。这 23 条全部转成 Jira 工单，关闭时附修复 commit 编号，审计才算闭环。安全 审计 误报 处理 别只记数量，每条假阳性都要写清为什么假，下次提示词里能直接复用。

总结

代码 安全 审计 让 AI 干的不是找漏洞，而是判真伪、补数据流：SAST 管广度，AI 管上下文，人管定级。范围切小、输出格式固定、误报补上下文而不是删规则，这三件事决定报告能不能看。仓库 安全 审计 流程 我固定成扫、判、核、验四步，每步都有产出物，换人接手也能跑。安全 审计 误报 处理 做扎实，团队才不会因为七成噪音放弃工具。
