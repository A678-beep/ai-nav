代码 评审 清单：分级检查项与执行流程

编程助手·更新于 2026-11-15·代码 评审 清单, 检查项 分级, 权限 校验, 代码 评审 模板, AI 辅助 评审, 代码 评审 检查项, AI 辅助 代码 评审

上个月我们一个订单详情接口出了越权：用户把 URL 里的订单号一改，能看到别人的收货地址。复盘时四个人都承认 review 过那个文件，但没人停下来问一句「这个资源属于当前用户吗」。那之后我把评审从凭感觉改成按 代码 评审 清单 走：18 条检查项分三级，写进 PR 模板，两周后首轮意见从平均 6 条降到 2 条，单次 review 从 35 分钟压到 12 分钟。

检查项分三级，P0 只留六条

P0 阻断六条：资源归属校验、SQL 参数化、密钥硬编码、数据迁移可回滚、金额用 decimal 不用 float、并发写幂等。P1 重要七条：空值和边界、异常被吞、N+1 查询、分页上限、日志里的敏感信息、新增分支测试覆盖、接口向后兼容。P2 建议五条：命名、注释、重复代码、圈复杂度、格式，这五条不进人工清单，交给 ESLint、ruff 和 SonarQube。分级是让评审有优先级：P0 无论 diff 多大都必须人工确认，P1 只查与改动相关的条目，P2 机器挡。每条代码 评审 检查项 都要写成可判定的问句，比如「新增接口是否校验了当前用户拥有该资源」，不写「注意权限」。18 条代码 评审 检查项 里，真正常用的其实就 P0 那六条。

把清单放进流程，别贴在墙上

落地三件事：仓库根目录放 .github/pull_request_template.md，P0 六条做成勾选项，勾选旁留一行写「怎么验的」；超过 400 行的 PR 退回拆分，一次看完 4 个文件是上限；评审顺序固定为机器先跑（ruff、ESLint、Semgrep，两分钟出结果）再 P0、再 P1，最后看 AI 建议。AI 辅助 代码 评审 我用 Copilot 和 CodeRabbit 打头阵，它们擅长空指针、未使用变量、明显的注入模式，意见按 P0/P1/P2 归类后再看，别让评论直接刷屏。但 AI 判断不了业务权限，P0 第一条必须人看。两周 23 个 PR 跑下来，这张 代码 评审 清单 拦下三个 P0：越权、金额浮点、迁移没写回滚，三个 AI 全没报。

三个案例和维护规则

越权那个案例固定成 P0 第一条，评审时问「这个 id 从哪来、校验归属了吗」；优惠券金额用 float 差 0.01 元，补了「金额字段必须是 decimal 或分」；列表接口 size 传 10000 直接打满数据库，P1 加了分页上限。代码 评审 清单 不维护就会变成摆设：每次线上 P0 事故追一条，超过 25 条就合并同类项，每季度删一次没人踩的条目。避坑一：清单别超过 25 条，超了没人看完。避坑二：别把风格问题塞进 P0，塞进去团队两周就不信这张表。避坑三：勾选必须写验证方式，只打勾等于没做。新同事入职第一周照着清单走，评审质量不再取决于当天谁有空。

总结

代码 评审 清单 的价值在可判定、分级、随事故更新。P0 六条人工全查，P1 按 diff 查，P2 交给工具，AI 辅助 代码 评审 负责找可疑点、人负责判断能不能上线。上次越权那种问题，清单上就一行字，但那一行能省一次线上事故和一次回滚。清单不用写漂亮，能让人停下来问一句就够了。
