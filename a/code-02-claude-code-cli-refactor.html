Claude Code CLI 重构：四步顺序

编程助手·Claude Code CLI 重构, Claude Code 重构, Claude Code 大仓库, Claude Code 重构大型项目, Claude Code 上下文不够

上个月我接手一个三万行的 Java 老仓库，要把工具类里的静态方法抽成服务。直接让 Claude Code CLI 重构 试了两次：第一次改到第 9 个文件就丢了前面的约束，第二次把没跑通的代码也写进了注释。后来我把流程拆成四步，才把 42 个文件稳定改完。Claude Code 重构大型项目 的第一步其实不是写代码，是让工具先看懂仓库边界。

第一步：把约束写进 CLAUDE.md

进仓库先跑 claude，再用 /init 生成 CLAUDE.md。别生成完就完事，我手动压到 60 行以内，只留三件事：构建命令 mvn -q compile、测试命令 mvn test -Dtest=OrderServiceTest、包结构约定 service 层不许直接注入 mapper。这三行比任何提示词都值钱，因为上下文压缩时它会被优先保留。我还在文件末尾写明：不许改 public 方法签名，每个类改完必须能编译。

后面发现新约束时不用重开对话，在输入框用 # 开头把规则追加进记忆就行。CLAUDE.md 超过 200 行反而拖慢启动，别把整本规范贴进去，只留每次必须遵守的那几条。最后把它提交进仓库，团队每人一份不如仓库里一份。

第二步：先出计划，再动代码

按 Shift+Tab 进 plan mode，让它只读代码、输出改造计划，存成 docs/refactor-plan.md。计划里要有文件清单、调用方、风险点，我要求每个文件一行，超过两行的退回重写。第一版计划它漏了 7 个调用方，我让它把所有引用点 grep 出来再排批次。确认后按文件分三批：第一批 5 个，第二批 12 个，第三批 25 个。每批开始前用 --add-dir 把公共库加进来，避免它以为工具方法不存在。Claude Code 上下文不够 的早期信号，是它开始改计划外的文件。

计划写完我还会让它列出回滚步骤：哪个 commit 能退、哪些文件必须手动恢复。这一步花 10 分钟，救过一次第三批改错连接池配置的事故。

第三步：分批提交，别一次到底

每批改完立刻跑测试，然后 git commit。Claude Code CLI 重构 的节奏是一次只动 3 到 5 个文件，改完用 /compact 压一轮上下文，再把 git diff 按文件看，每批不超过 300 行。整个仓库花了约 6 小时，用的 Pro 订阅每月 20 美元，没触发 5 小时窗口的上限。Claude Code 重构大型项目 时，最贵的不是 token，是我 review 的时间，所以宁可多分两批。

三个坑也集中在这一步：一是 Claude Code 上下文不够 时会把早期约束忘掉，另一种表现是开始重复问同一个问题，约束要写进 CLAUDE.md 而不是聊天里；二是别让它一次改整目录，文件越多越容易漏调用方；三是订阅额度按 5 小时滚动窗口算，长任务别和聊天共用同一时段。补一条：动手前一定先建分支，它偶尔会顺手改配置文件。

总结

Claude Code CLI 重构 的稳定流程是：CLAUDE.md 锁约束、plan mode 出计划、按文件分批、每批测试加提交。最后 42 个文件全部改完，测试通过率从 61% 回到 98%，返工最多的一轮，正是没写计划的那次。
