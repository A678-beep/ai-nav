代码 转 伪代码：1.2 万行老系统的读法

编程助手·更新于 2026-11-15·代码 转 伪代码, 伪代码 粒度, 遗留代码 理解, 代码 评审, 伪代码 粒度 标准, 伪代码 评审 清单

接手一个 1.2 万行的 Java 订单模块，18 个核心类，前任离职，注释有三成已经过期。第一周硬读，两天只理清 6 个类的调用关系，改一个退款状态还要问三个同事。后来把 AI 代码 转 伪代码 当入门工具，三天出一份 8 页伪代码，新人对着它 5 天上手，原来要两周。

粒度：一个函数一块，5 到 15 行

伪代码 粒度 标准 我按函数定：一个方法一块，分支一行一条，循环不展开，异常路径单独标。单块 5 到 15 行，超过多半是业务真复杂，或者模型在把代码换个写法复述。输入给函数本身加它的调用方，一次 150 到 250 行；超过 400 行，模型开始漏分支，我实测三个 catch 被吞掉两个。结构固定六段：前置条件、输入、步骤、输出、异常、副作用。案例：600 行 Go 支付回调转成 2 页伪代码，业务方 20 分钟就确认了退款口径。避坑一：让模型保留 for 循环和临时变量，转出来还是代码，读的人照样卡；避坑二：一个类 2000 行一次全转，它会把两个方法的逻辑并成一段，交接时最坑。

命名：换成业务词，别照抄变量名

代码 转 伪代码 最容易糊弄的地方是命名。规则三条：动作用动词加业务对象，校验优惠券时效、冲正退款单，不写 check()、doFix()；领域词保留原样，履约、核销、账期这类词不要翻译；同一份文档命名风格统一。提示词里加一句：用业务语言改写，保留所有 if、else、异常分支，不许省略，不许优化逻辑。输出要 Markdown，编号到二级分支，比如 3.1 不可用则回滚。避坑：模型爱合并相邻分支，写个合并的步骤省字数，评审时最容易漏掉边界；模型也会顺手优化，把重试三次写成重试，语义直接变了。案例：一段 300 行 Python 对账脚本转完，业务方指着 4.2 说这条规则我们三年前就废了，代码里还留着。

评审：三关对照，过完才进文档

伪代码 评审 清单 三关。第一关溯源：每块标文件名和行号范围，随便抽一条能翻回原代码。第二关分支覆盖：数代码里的 if、else、catch、switch 分支，和伪代码步骤一一对上，覆盖不到 100% 就打回。第三关业务确认：把状态流转和金额规则讲给业务方听，他们点头才算过。案例：8 个类评审出 5 处问题，2 处是模型漏了 switch 的 fallthrough，1 处把重试 3 次写成重试，2 处业务规则理解反了，修完才进交接文档。避坑：复杂 SQL 单独列一块，塞进主流程会淹没判断条件；伪代码保留关键表名和字段名，新人排查能直接搜。这套 代码 转 伪代码 的做法跑过两个老系统，交接文档从没人看变成每周有人翻。

总结

代码 转 伪代码 就三件事：粒度压到函数级，命名换成业务词，评审过三关。伪代码 粒度 标准 定死后，模型输出稳一半；伪代码 评审 清单 别省，漏一个分支就是线上事故。它帮你读懂代码，替代不了跑测试。
