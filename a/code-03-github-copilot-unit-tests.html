GitHub Copilot 单元测试：三步法

编程助手·更新于 2026-11-15·GitHub Copilot 单元测试, Copilot 生成测试, Copilot 测试用例, Copilot 单元测试覆盖率, Copilot 测试用例不准

订单模块的老代码没有测试，我先用 GitHub Copilot 单元测试 补了一轮，结果 38 个用例全绿，覆盖率从 42% 涨到 71%，但上线第二天就发现一个金额取整的 bug，测试根本没碰到。写这篇记录，是想说清楚 Copilot 生成的测试要怎么调教才算数。

先给测试框架立规矩

在 VS Code 的 settings.json 里加 github.copilot.chat.testGeneration.instructions，写清三句话：用 pytest 加 factory_boy，不要 mock 数据库，金额字段一律用 Decimal。打开被测文件，在 Copilot Chat 里输 /tests，或在编辑器右键选 Copilot → Generate Tests，一次会生成 30 到 40 个用例。不写指令它会默认用 unittest 加 MagicMock，那 38 个用例里有 12 个是重复断言；改完指令后重复降到 3 个，还会自动给边界值补参数。

生成 38 个用例大约 90 秒，比我手写快五倍，但它只读当前文件，跨模块的 fixture 要手动补。跑之前先确认 pytest 版本，它偶尔生成 pytest 8 才有的写法，老项目直接报语法错。这个设置项只对测试生成生效，不影响普通补全，团队共用就写进 .github/copilot-instructions.md。

让失败用例当线索

生成后先整体跑一遍，别急着看覆盖率。我那批里有 9 个一跑就报错，5 个是它假设错了参数顺序，剩下 4 个正好暴露空列表和负数金额两个真实分支。把错的改成断言当前真实行为，再补边界：0、-1、999999.99、两位小数、负数退款，自己列一遍再让它按列表补，比让它自由发挥稳。Copilot 单元测试覆盖率 从 42% 到 71% 只花了 20 分钟，但把假断言换成有效断言又花了四十分钟，这两段时间的比例基本就是这类工具的真相。覆盖率的分子分母也要看清：它只统计执行过的行，不统计断言写得对不对。

还有个土办法判断深浅：手动把金额四舍五入改成截断，再跑一遍测试，38 个用例里只有 2 个变红，说明广度够、深度不够。同样的变异测试拿去改状态码，红了 6 个，这部分才是我能放心上线的。

三个坑

跑完这套，GitHub Copilot 单元测试 对我来说就是个起稿器。三个坑排前面：一是断言照抄现有实现，把 bug 写成预期，生成完先搜有没有"金额等于原值"这种废话断言。二是 mock 过度，数据库、消息队列全 mock 掉，测试只证明 mock 能工作。三是时区问题，订单时间用 UTC 还是本地时间，生成的断言经常默认本地时区，跑到 CI 就红。另外免费版每月 2000 次补全加 50 次聊天，Pro 每月 10 美元不限补全，批量生成建议用 Pro；也别让它把生产数据的手机号写进 fixture。Copilot 单元测试覆盖率 只适合当参考，Copilot 测试用例不准 的时候，先看看丢给它的需求是不是只有一句话。

总结

GitHub Copilot 单元测试 的正确用法是先立框架规矩、再让失败用例说话、最后人工补边界。遇到 Copilot 测试用例不准 的情况，先把指令改具体，再用变异测试验收，假绿的坑就能少踩一半。
