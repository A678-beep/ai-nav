AI 生成 SQL 校验：执行计划与权限红线

编程助手·更新于 2026-11-15·AI 生成 SQL 校验, SQL 执行计划, 边界 条件, 权限 校验, SQL 执行计划 检查, SQL 权限 校验

上周评审一条 AI 写的清理脚本，DELETE FROM orders WHERE status = 0，没有时间条件，预跑 COUNT 是 42 万行，实际该删的只有 1.2 万行。SQL 语法没问题，执行计划也不难看，但真执行下去就是事故。AI 生成 SQL 校验 我固定成三道闸：执行计划、边界清单、权限和发布动作。

执行计划先跑，能跑不等于能上

EXPLAIN 看三处：type 出现 ALL 或大表上的 index 直接打回；rows 接近表行数说明在扫全表；Extra 里有 Using filesort、Using temporary 要问清楚排序和去重能不能走索引。再细一层，看 key 用没用上、key_len 多少、filtered 估计的过滤比例，最后对比扫描行数和返回行数，差距大就是白扫。案例：订单表 860 万行，模型写的月度统计 SQL 是 type=ALL、rows 860 万、filtered 2%，实跑 41 秒；时间范围改成 created_at >= ? AND created_at < ?，加上 (status, created_at, user_id) 联合索引，再让它重写，降到 0.6 秒。MySQL 用 EXPLAIN ANALYZE 看真实耗时，PostgreSQL 用 EXPLAIN (ANALYZE, BUFFERS)，估算和实测差两倍以上就重新分析。坑一：分页最容易漏，LIMIT 200000, 20 会先扫 20 万行，改成 WHERE id > ? 的游标分页。执行计划原文我会贴回模型，让它逐列解释，解释不出来的地方就是手工查的地方。

边界条件按清单逐条过

边界 条件 清单八条：NOT IN 遇到 NULL 返回空集；LEFT JOIN 的右表条件写进 WHERE 会退化成 INNER JOIN；除零、空串、超长字符串截断；时区，created_at 存 UTC 而报表按 Asia/Shanghai 出数；varchar 字段传数字触发隐式转换、索引失效；没有 LIMIT 的查询直接返回百万行；批量更新不分批；重复执行不幂等。再补两条：金额用 DECIMAL 别用 FLOAT，汇总四舍五入多次会差出几分钱；单条 INSERT 别超过 500 行，不然锁等待明显。案例：模型写的用户报表把 b.status = 1 写进 WHERE，LEFT JOIN 退化成 INNER，漏掉 1.3 万条没有订单的用户，和报表口径对不上，改成 b.status = 1 OR b.id IS NULL 才对。坑二：别只拿空表测，用 10 万行数据跑一遍，空表能过，有数据才暴露慢查询和锁等待。

权限和发布动作卡死

AI 生成 SQL 校验 的第三道闸是权限。跑 SELECT 用只读账号，账号按库授权，禁止跨库查询，导出权限单独申请；DML 先在事务里开 SELECT COUNT(*) 圈定影响行数，再执行，核对数字和预期一致才提交。UPDATE、DELETE 必须带 WHERE 和 LIMIT，禁止出现 1=1；DDL 由人工单独审，不交给模型。大表改数据先建临时表分批写，每批 5000 行，跑完再切。案例：同事清理测试数据，它给的 DELETE 少了 created_at 条件，预跑 COUNT 42 万行，加上条件后 1.2 万行，先在事务里 SELECT 校验再提交。SQL 权限 校验 还有一条：生产库连接串别直接贴给云端模型，表结构用脱敏后的 DDL。上线前再跑一次 SQL 执行计划 检查，确认没退化成全表扫描，写进发布检查单。

总结

AI 生成 SQL 校验 就三道闸：执行计划看 type、rows、Extra，边界按八条清单逐条对，权限用只读账号和事务圈定影响行数。那条 42 万行的 DELETE 最后没出事，靠的不是模型变聪明，是发布前多问了一句影响多少行。SQL 权限 校验 和 SQL 执行计划 检查 一起写进发布单，每条 SQL 留一份 EXPLAIN 和执行记录，出事能倒查。
