接口 文档 同步：OpenAPI 双闸校验

编程助手·更新于 2026-11-15·接口 文档 同步, OpenAPI 3.0, oasdiff, CI 校验, 接口 文档 一致性 校验, OpenAPI 版本 管理

上周前端在联调群里问我：文档里 idempotencyKey 还是必填吗？我打开 Redoc 才发现，文档停在上个迭代，代码里这个字段三个月前就改成可选了。回头统计，11 个仓库、312 个接口，有 27 个的文档和实际响应对不上，最老的一处停在去年十月。之后我把接口 文档 同步 交给机器：人只改一处，其余由生成器和流水线守着。

先定唯一源头：spec 提交进仓库

两种流派都试过，最后选代码先行：所有服务统一导出 OpenAPI 3.0，Spring Boot 3.2 配 springdoc 2.3.0，描述写在注解里；Python 用 FastAPI 自带的 /openapi.json；Go 用 swag init。构建时 make doc 把 spec 导出到 docs/openapi/ 下按服务拆分并提交，前端 SDK、Mock、Redoc 页面都从这份文件长出来，wiki 上的手写文档一律停更。

参数只改三处：servers 从 127.0.0.1:8080 换成 ${API_HOST} 由 CI 注入；字段必填以 Bean Validation 为准，@Schema 的 requiredMode 只做展示；securitySchemes 收进公共组件，避免每个接口重复写。坑有两个：绕过生成器直接改 json，下次导出被覆盖，diff 里还看不出来；中文 description 里的全角引号会让 Redoc 锚点错位。pre-commit 加一条检查：docs/openapi 有变更但 controller 目录没变更就拦下。这步做完，接口 文档 同步 才算有了地基。

CI 两道闸：生成比对与破坏性检测

第一道闸最短：CI 跑 make doc，再 git diff --exit-code docs/openapi。退出码非 0 就失败，说明有人改了注释没导出，或者手改了 spec。11 个仓库串行跑 40 秒，比人工 review 靠谱得多。

第二道用 oasdiff breaking 对比主干 spec，删字段、改类型、枚举收紧、必填新增都会退出 1 阻止合并，上线半年拦下 9 次，其中 4 次前端已经按旧 spec 发了版。redocly lint 顺手查 operationId 重复、缺 4xx 响应、示例用了真实手机号，自定义规则开 6 条，跑一遍 12 秒。预发再加一层：schemathesis 拿 spec 对 47 个接口跑属性测试，500 响应也会被 schema 校验拎出来，三个月抓到 3 个文档没写的 500 分支。这套 CI 校验 和 接口 文档 一致性 校验 能挡住漂移，但挡不住业务含义写错，那部分还得人看。

版本按 tag 走，弃用提前两个迭代

文档不跟分支，跟 git tag：镜像 v2.4.0 对应 docs/openapi/v2.4.0/，Redoc 后台按 tag 出快照页，线上保留最近 6 个版本，前端切版本不用再问后端。这是 OpenAPI 版本 管理 的底线，比“文档永远最新”实用。

弃用走三件套：响应头加 Deprecation 和 Sunset，spec 里标 deprecated: true，changelog 写清替代接口和下线日。结算接口从公告到下线留了 63 天，openapi-generator 生成的 SDK 会在编译期打警告，前端提前一个迭代迁完。机制上线三个月，文档不一致工单从 43 起降到 6 起，平均修复从 4 天压到 8 小时；新增接口的文档耗时从 5 天变成 0。两个坑：文档发布挂在部署之后，服务回滚了页面还是新的；版本入口写 latest，CDN 缓存能让你干等 24 小时。

总结

现在固定四件事：spec 单一源头、CI 生成比对、oasdiff 破坏性检测、tag 加 Sunset 弃用。接口 文档 同步 的目标不是文档好看，是文档对不上时代码合不进去。等 接口 文档 一致性 校验 变成合并请求里的固定一步，OpenAPI 版本 管理 才有讨论的意义。
