代码 审查 Agent：规则到 CI 的落地

编程助手·更新于 2026-11-15·代码 审查 Agent, 审查 规则, 误报率, CI 闸门, Agent 代码 审查 误报, Agent 代码 审查 接 CI

团队四个人、两周一迭代，一个迭代 42 个 PR，平均每个 380 行、6 个文件，人工首轮 review 要 35 分钟。我把 代码 审查 Agent 接进流程后，单个 PR 90 秒出 9 条意见，但第一版 38 条里 13 条是误报。这篇写规则怎么定、误报怎么压、CI 闸门怎么设。

规则文件：22 条能验证的，不写正确的大词

代码 审查 Agent 规则 放在仓库根目录的 AGENTS.md，子目录再放专项文件；Copilot 那套放 .github/copilot-instructions.md。22 条分四组：安全 5 条（注入、越权、密钥硬编码、日志脱敏、反序列化）、边界与异常 7 条、性能 4 条、可维护性 6 条。每条带编号、触发条件、反例和豁免说明，比如 SEC-03 要求接口按资源归属校验，豁免是明确的公共只读接口。规则要写成能验证的动作，别写“代码要优雅”，这种话 Agent 只会回一句已检查。跟只看 diff 的机器人比，它能跑 ruff 和 pytest、能翻全仓调用链，误报少一截；代价是必须要求每条意见附证据行号和代码片段。输出统一 JSON：rule_id、severity、file、line、evidence、suggestion。坑：规则写超过 200 行它记不住，我拆成根目录 60 行加三个子目录文件才稳。

误报：三列台账，三处补丁

广告位（文章中部）AdSense / 广告联盟代码插入点 · 建议 728×90 / 移动端 320×100

Agent 代码 审查 误报 首月 34%，13 条分三类：不懂业务封装 6 条、测试文件风格 4 条、同一行重复报 3 条。台账记三列：规则编号、误报原因、补丁动作。第一处补丁是路径说明，告诉它查询统一走 db.query 已参数化、权限注解在网关校验；第二处是排除目录，dist、*.lock、migrations 不进审查；第三处是等级映射，风格类降到 info 且不发评论。改完误报率 8%，单个 PR 评论从 9 条降到 4 条，人工从 35 分钟压到 12 分钟。避坑：误报不沉淀，两周后没人看评论；每月花 30 分钟把高频误报写回规则文件，比换工具管用。台账每两周过一遍，同一规则反复误报就直接改规则，别靠人肉记忆。

CI 闸门：只阻断 P1，别让 Agent 签字

Agent 代码 审查 接 CI 我放在 GitHub Actions：pull_request 触发，先跑 lint 和测试，再让 Agent 只读审查，超时 5 分钟，结果存 JSON 上传 artifact，评论用 reviewdog 发到对应行。闸门只拦 P1：安全、越权、金额计算、并发写；P2 只评论不阻断，P3 直接归档。坑一：超过 500 行的 PR 它开始漏看，我按文件拆成多个 PR 再送审。坑二：别给它写权限、别让它自动提交，patch 只做建议，人改人签。坑三：私有仓先确认代码留存条款，走不通就用自托管 Qodo Merge 或本地模型。成本不高：4 万 token 约 0.1 元，月 200 个 PR 二十来块。一个迭代 42 个 PR，它抓了 3 个 P1：优惠券核销没加锁、导出接口分页没上限、日志打了身份证号；也漏了一个前端缓存键问题，靠人工补，之后把这条写进了规则。

总结

代码 审查 Agent 的顺序是：先写规则文件、再压误报、最后接 CI 闸门。Agent 代码 审查 接 CI 的关键不是跑得快，是只拦真正要拦的；Agent 代码 审查 误报 压不到一成，团队就会把它当墙纸。三个数记住：规则 200 行以内、误报 8%、只阻断 P1。
