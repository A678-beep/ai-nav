提示词 版本 管理：团队落地 3 个动作

对话AI·更新于 2026-11-15·提示词 版本 管理, 提示词 版本 控制, 提示词 回归 测试, Jinja2, 提示词 版本 控制 工具, 提示词 回归 测试 用例

团队 6 个人维护 40 多条客服和文案提示词，全躺在飞书文档里，文件名从 v1 到 v2、final、final2、最终版。上周线上话术效果掉了一截，没人说得清是哪次改动，只能把文档翻出来一条条试。我把提示词 版本 管理 搬进 Git 仓库，配上渲染脚本和 40 条回归用例，两周才跑顺，下面是真正落地的三个动作。

先定目录：一条提示词一个文件

提示词 版本 管理 的第一步是把目录定死。仓库第一层按业务域分，prompts/service/、prompts/marketing/、prompts/internal/，每条提示词一个 YAML 文件，文件名 p_refund_reply.yaml，文件名里不写版本号，版本号只交给 Git 的 commit 和 tag，这样就不会再出现 p_refund_v3_final.yaml。文件头固定五个字段：id、model、temperature、owner、updated_at，下面才是 system prompt 原文。提示词 版本 控制 工具 不用另找，Git 的 diff 和 tag 就是最稳的那套：分支只留 main 和 dev，发布打 tag，格式 prompt-2026.02.1，回滚就是 git checkout 对应 tag 再渲染一遍。

变量显式声明：别在 prompt 里硬编码

广告位（文章中部）AdSense / 广告联盟代码插入点 · 建议 728×90 / 移动端 320×100

变量统一用双大括号占位，渲染脚本走 Jinja2 的 StrictUndefined，少传一个变量直接报错，不会静默渲染成空字符串。每个变量在文件头的 inputs 段声明类型和长度：customer_name 字符串 20 字以内，order_amount 数字保留两位小数，refund_type 枚举三选一。渲染命令是 python render.py --id p_refund_reply --set customer_name=张三，测试和线上共用同一套渲染逻辑。三个坑：变量名别用中文和空格；变量值本身含双大括号会触发二次渲染报错，输入前要先转义；20 字上限不是写着好看，称呼字段超过 20 字会被客服工作台截断，提示词里再让模型称呼客户全名就会打架。这一层做完，提示词 版本 管理 才算有了可维护的输入边界。

回归测试：40 条用例挡住回滚

每条提示词旁边放 tests/p_refund_reply.json，40 条输入，期望写成必须提到退款时效这类要点，不比对精确文本，因为温度不是 0。跑法固定 temperature 0.2、每条采样 3 次、取多数结果，改动前后跑同一批用例，通过率直接对比。上周把退款话术从 v6 升到 v7，新增一句先解释政策再给方案，通过率从 34/40 到 37/40，但平均输出从 180 字涨到 243 字，客服嫌啰嗦；把这句改成必要时解释政策，字数回到 196，通过率保持 36/40，才合进 main。提示词 回归 测试 用例 的价值在这里：它不保证变更更好，但能挡住变差。两个避坑：用例里不能出现线上真实手机号和订单号，脱敏后再存仓库；模型从 deepseek-chat 的旧快照换到新快照也要重跑用例，但模型版本不写进提示词版本号。

总结

团队现在的流程固定了：改文件开分支、本地渲染一遍、40 条用例全过才合 main，tag 用 prompt-2026.02.1 的格式。提示词 版本 管理 说到底三件事：文件进仓库、变量显式声明、用例先跑再合。提示词 版本 控制 工具 就 Git 一套，别急着买平台。两条红线别碰：测试用例别和 prompt 写进同一个文件，模型别用 latest 别名。提示词 回归 测试 用例 跑一次 6 分钟，一周省下的排查时间远不止这点。
