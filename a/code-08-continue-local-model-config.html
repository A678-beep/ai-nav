Continue 本地模型 配置：双模型分工

编程助手·更新于 2026-11-15·Continue 本地模型, Continue 配置, Ollama 补全, Continue 本地模型 配置教程, Continue 补全延迟高

笔记本只有 8GB 显存，我一直觉得本地补全是个玩具。直到把 Continue 本地模型 配置 拆成两个角色：7B 负责聊天和改写，1.5B 专门做行间补全，两分钟装完，延迟从云端方案的 400ms 降到 150ms 左右。这篇把配置文件和显存账一起写清楚，8GB 卡照着抄就能跑。

装 Ollama 与两个模型

先装 Ollama，ollama --version 确认版本在 0.5 以上，然后拉两个模型：ollama pull qwen2.5-coder:7b 和 ollama pull qwen2.5-coder:1.5b，前者 4.7GB、后者 1.4GB，家里 300M 宽带大概 6 分钟。7B 的 Q4 量化运行时占 4.7GB 显存，1.5B 只占 1.4GB，两个同时加载 8GB 卡刚好停在 6GB 出头，剩下 2GB 留给系统和浏览器。如果你的卡是 6GB，只装 1.5B 做补全、聊天继续用云端，别硬塞。模型文件默认放在用户目录，C 盘紧张就把 OLLAMA_MODELS 环境变量指到 D 盘，改完重启 Ollama 服务。

Continue 配置文件在 ~/.continue/config.yaml，关键是 roles 字段，它决定哪个模型接哪类请求，选错角色比选错模型更常见。

装完先跑 ollama run qwen2.5-coder:1.5b 随便问一句，确认模型能响应再配 Continue，省得在 IDE 里排查半天。第一次加载 7B 要 3 到 5 秒，之后常驻内存，切换项目不用重新加载；如果发现每次补全都卡一下，说明模型在被反复卸载。

config.yaml 怎么写

yaml
models:
  - name: qwen-7b
    provider: ollama
    model: qwen2.5-coder:7b
    roles: [chat, edit, apply]
    defaultCompletionOptions:
      contextLength: 8192
  - name: qwen-1.5b
    provider: ollama
    model: qwen2.5-coder:1.5b
    roles: [autocomplete]

补全模型必须选 FIM 训练过的 coder 系列，拿通用模型做 autocomplete 会补出一大段而不是续几行。roles 里 autocomplete 只能挂一个模型，多挂会按顺序挑第一个；chat 和 edit 可以共用 7B。Ollama 默认上下文只有 2048，大文件会被截断，把 contextLength 调到 8192 是第一步。Continue 补全延迟高 多半是模型选错：1.5B 的首次建议约 150ms，换成 7B 直接 800ms 起，打字会明显卡顿。补全的触发延迟在设置里还能调，默认值偏保守，改到 200ms 左右手感最好。保存配置后 Continue 状态栏会显示当前配置名，点开能看到每个模型挂了哪些角色。

三个坑

一是别让 7B 兼任 autocomplete，风扇声会告诉你答案。二是 Ollama 的 keep_alive 默认 5 分钟，模型卸载后再加载要 3 秒，长会话记得设成 -1。三是中文注释会让补全偏向生成中文，需要代码时用英文注释引导。

Continue 本地模型 配置教程 我建议先照抄，再按 Continue 补全延迟高 的原因逐项调。我收藏的 Continue 本地模型 配置教程 只有两篇，其他多半过时。显存账要自己算：14B 至少要 9GB，8GB 卡别硬上。另外别忘了留 2GB 给 IDE 本身，VS Code 加浏览器一起开，显存挤爆会直接退到 CPU 推理，延迟翻十倍。四是配置文件改完不用重启 IDE，保存后点一下 reload 就生效，但改了模型名要重新拉取，否则会静默回退。五是 16GB 内存的机器同时开 Docker 会把内存挤爆，推理速度掉一半。第一次装建议先只配补全模型跑一天，再加聊天模型，出问题好排查。

总结

Continue 本地模型 配置 的核心是分工：小模型管速度、大模型管质量，配置文件里用 roles 隔开。现在断网也能补全，代码不出本机，唯一代价是聊天质量比云端差一截。Ollama 补全 跑顺之后，最明显的变化是补全不再打断思路，我连开会都敢开着编辑器写代码了。
