日志 分析 AI：先聚合再让模型定位故障

编程助手·更新于 2026-11-15·日志 分析 AI, 日志 格式, 聚合 查询, 提示词 模板, 脱敏, AI 日志 排查, 日志 聚合 分析

支付回调接口 502 从 0.3% 涨到 8%，凌晨两点值班，三个服务十二个 Pod，一天 1.4 亿行日志。我先 grep 关键字，翻到第 4 万行没头绪；又把 3 万行原始日志整段贴给模型，它编了两个不存在的字段名。后面把 日志 分析 AI 改成先聚合再提问，40 分钟定位到连接池打满，502 回落到 0.2%。

字段先定死，日志才是数据

日志 格式 不统一，再强的 日志 分析 AI 也看三行就乱。我固定 JSON Lines，一行一条，必填 12 个字段：ts 用 ISO 8601 带时区、level、service、trace_id、span_id、method、path、status、latency_ms、error_code、msg、pod。字段名统一 snake_case，别一个服务用 ts、另一个用 timestamp。trace_id 按 OpenTelemetry 规范用 32 位十六进制、span_id 16 位，链路才串得起来。三个坑：Java 多行堆栈用 JSON encoder 或采集端 multiline 合并，按行切会把异常和请求拆散；时区统一到 +08:00，UTC 混用差 8 小时，我曾把 14:20 的发布看成 22:20；URL 别打完整 query，token 常在那里。改完每天 1.4 亿行约 38GB，压缩后 6.8GB，ClickHouse 保留 7 天，查 2 小时窗口 30 秒内出。

先聚合，再喂模型

日志 分析 AI 的前提是别喂原始日志。先按分钟、status、error_code 分组：ClickHouse 用 SELECT toStartOfMinute(ts) m, status, error_code, count() c FROM logs WHERE ... GROUP BY m, status, error_code；Loki 用 sum by (status) (count_over_time({app="payment"} |= "502" [1m]))。再取 Top 20 错误签名，msg 去参数化，订单号、用户 ID 换成 {id}，每个签名带 3 条样本。2 小时 1200 万行压成 240 行，提示词从 3 万 token 降到 2.4k，成本只剩十分之一，编字段从 10 次里 4 次降到不到 1 次。聚合结果再按时间桶对齐发布记录，一眼能看出是不是新版本带进来的。避坑一：采样日志算比例会失真，比例用计数器取。避坑二：只看 5xx 会漏，部分 4xx 才是真实业务失败。日志 聚合 分析 这一步做粗，模型后面只能给空话。

提示词三段式，结论要带证据

提示词 模板 固定三段：角色加已知（时间线、发布记录、聚合表）、约束（只根据下文推断，按假设、证据、验证 SQL、下一步四段输出，引用字段名，不确定写需验证）、输出格式。加一句我每次必带的：“先列三个可能原因，按可能性排序，每个原因给出能在只读库执行的查询，不要直接给根因。”那晚聚合显示 14:20 后 502 集中在 pod-3，error_code 1013 是上游连接超时。模型三个假设里第二个是下游连接池耗尽。验证：连接池每 Pod 40，扩到 15 个 Pod 峰值 600，下游 MySQL max_connections 只有 500，报错对上了。连接池降到 30、读请求走从库，502 回到 0.2%。避坑一：生产日志脱敏再外发，手机号、Authorization、身份证号先替换，别整段丢公网模型。避坑二：模型给的 SQL 先在只读副本 EXPLAIN，字段名它可能编。AI 日志 排查 省的是翻日志的时间，验证还得自己跑。

总结

日志 分析 AI 的顺序是：字段定死、聚合查询、Top 签名、三段式提示词、只读库验证。两个不要：不要把原始日志整段丢给模型，不要把模型结论当根因直接执行。日志 聚合 分析 做对，2 小时数据能压到 240 行给模型；AI 日志 排查 快是快，最后那步 EXPLAIN 和指标核对还得人来做。这套流程跑半年，平均定位时间从 3 小时半降到 40 分钟，误报告警也从每周 47 条降到 6 条。
