OpenAI Codex CLI 沙箱：写工作区

编程助手·更新于 2026-11-15·Codex CLI 沙箱, Codex CLI 权限, Codex CLI 配置, Codex CLI 沙箱模式, Codex CLI 审批策略

装完 Codex CLI，第一次跑 codex 它默认待在只读沙箱里，改不了任何文件；加参数放开之后又能写工作区了，但 npm install 全部失败。OpenAI Codex CLI 沙箱 的三种模式我挨个试了一遍，最后固化出一份 config.toml，这篇把权限和网络的组合讲清楚，免得你也卡在“能写不能装”这一步。我把三种模式在同一个 Node 仓库上各跑了 20 分钟，数据在下面。

三种沙箱模式怎么选

read-only 只能读、不能写、不能联网，适合让它分析陌生仓库；workspace-write 能写当前目录和临时目录，网络默认关闭；danger-full-access 等于不设防，只在容器里用。我日常用第二条，命令是 codex --sandbox workspace-write。Codex CLI 权限 的另一半是审批策略：untrusted 只放行只读命令，on-request 由模型自己申请，on-failure 失败后申请，never 从不问，只有 CI 才用最后一条。Codex CLI 审批策略 的四个档位里，我实测 on-request 最顺手，它会先说明要跑什么再申请。

三种模式我在同一个 Node 仓库各跑了 20 分钟：read-only 读了 12 个文件、写了 0 个；workspace-write 改了 9 个文件，其中 2 次超出范围被拒绝；danger-full-access 最快，但把 3 个临时文件也删了。

两种设置是相乘的关系，不是二选一：沙箱决定能碰什么，审批决定碰之前问不问。我试过只放宽沙箱、审批保持 never，结果它默默改了三个配置文件。

config.toml 与 profile

广告位（文章中部）AdSense / 广告联盟代码插入点 · 建议 728×90 / 移动端 320×100

把默认值写进 ~/.codex/config.toml：

toml
sandbox_mode = "workspace-write"
approval_policy = "on-request"

再配两个 profile：conservative 用 read-only 加 untrusted，跑陌生仓库；trusted 用 workspace-write 加 on-request。切换用 codex --profile conservative，写好后日常启动改成 codex --profile development 更稳定。工作区沙箱默认断网，需要装依赖时开 [sandbox_workspace_write] network_access = true，或者干脆把依赖装好再进沙箱。OpenAI Codex CLI 沙箱 的核心配置只有两个键，其余都是组合，这两个键错一个，行为就完全不同。Codex CLI 沙箱模式 选对了，误删文件的风险能降一大半；配错的典型症状是它反复申请权限，而你一直点同意。

三个坑

一是沙箱里 npm install 卡住不是网络问题，是策略问题，先看日志里的 denied。二是 danger-full-access 加 approval_policy = "never" 是危险组合，脚本里千万别这么写。三是沙箱只隔离文件系统和命令，不隔离代码上传，私有仓库先看数据条款。

另外 codex exec 跑批量任务时，read-only 加 never 才是 CI 的正确姿势，别在流水线里开写权限。Codex CLI 审批策略 按环境分三套，比一套走天下安全得多。四是 codex exec 在 CI 里默认以仓库根为工作目录，跨目录任务记得显式传路径；五是沙箱里的 MCP 服务连不上本地端口，别在沙箱里调本地 API。被拒绝的命令在日志里会标 denied，先搜这个关键字比猜快。Codex CLI 沙箱模式 按项目分，别一个配置跑所有仓库。还有订阅额度问题：ChatGPT Plus 每月 20 美元能覆盖日常量，重度使用要么升 Pro，要么换成 API key 按量付费。

总结

OpenAI Codex CLI 沙箱 的默认值偏保守，真正要改的只有两处：模式换成 workspace-write，审批保持 on-request。把配置写进 config.toml 存成 profile，比每次命令行拼参数可靠得多。
