代码 搜索 工具 对比：grep 到语义检索

编程助手·更新于 2026-11-15·代码 搜索 工具 对比, ripgrep, 语义搜索, VS Code 搜索, ast-grep, 多仓库 代码 搜索 方案, grep 搜索 大仓库 太慢

上月排查一个重复扣款的线上问题，grep -r 在 40 个微服务、约 800 万行代码里扫了 47 秒，还把 node_modules 里的误命中翻出一堆。换 ripgrep 后 1.6 秒出结果；再后来试语义检索，一句中文描述就能列出候选文件。这篇 代码 搜索 工具 对比 只回答一个问题：什么场景该用哪一种。

精确匹配：grep 与 ripgrep

只要知道符号名或字符串，ripgrep 就是最优解：rg -n -C 3 -t java -g '!vendor' 'payCallback' 一条命令带行号和上下文，默认并行、默认尊重 .gitignore、自动跳过二进制，800 万行 1.6 秒，冷缓存 3.1 秒。grep 搜索 大仓库 太慢 的原因很实在：grep -r 不读忽略规则，node_modules 和 dist 全扫，还只有单线程，同样条件 47 秒，差 29 倍。要注意 rg 默认不搜 .gitignore 里的文件，生成代码和本地配置会漏，加 -uu 才搜全；用 (?<=xxx) 这类后向断言会直接报不支持，加 -P 走 PCRE2 引擎就行。常用参数还有 rg -l 只列文件名、rg --stats 看耗时和命中数；在仓库根放一个 .rgignore，把 dist 和生成代码排掉，比每次敲 -g 省事。

语义检索的适用边界

不知道函数叫什么、只知道业务描述时，grep 和 rg 都无能为力。Cursor 的 @Codebase、VS Code 里的 Copilot @workspace 都是把仓库切块做向量索引，问“支付成功后回调为什么会重试”能直接给出 12 个候选文件，其中 8 个相关。代价是建索引慢，2.8 万个文件的仓库首次索引 6 分钟左右，之后增量；索引没覆盖的分支或仓库，它一定搜不到，团队做 多仓库 代码 搜索 方案 时先统一索引范围。Continue 插件里的 @codebase 走的也是向量检索，索引文件落在本地项目目录，换台机器要重建一遍。语义检索也搜不了精确常量，查 PAY_RETRY_MAX 等于几，它给的答案是猜的。所以 代码 搜索 工具 对比 到语义这一层，比的其实是索引覆盖范围。

重构场景和三个坑

改结构而不是改字符串，用 ast-grep：ast-grep -p 'if ($X == null) { return; }' -l java 按语法树匹配，比正则稳，还能直接 --rewrite。我的落地顺序是：符号定位用 rg，不知道名字的逻辑用语义检索，跨 40 个仓库时把仓库拉到同一父目录，rg -l 一把扫完；要搜历史提交再用 git log -S。三个坑：一是 rg 默认跳过 .gitignore，搜配置前确认没被忽略；二是中文注释如果是 GBK 编码，命中会乱码甚至漏，加 --encoding gbk；三是 GitHub 网页代码搜索只索引默认分支，hotfix 分支里的改动别指望它。另外 rg 的 --type 预设和 VS Code 的 search.useIgnoreFiles 设置要一起看，编辑器里搜不到，多半是同一份忽略规则在起作用。回到 grep 搜索 大仓库 太慢 这件事，29 倍差距全在忽略规则和并行上。

总结

代码 搜索 工具 对比 的结论很简单：知道名字用 rg，不知道名字用语义索引，改结构用 ast-grep，跨仓库靠统一目录和 .rgignore 收敛范围。多仓库 代码 搜索 方案 里最容易被忽略的是索引权限和分支覆盖，先确认这两点，再谈工具好坏。
