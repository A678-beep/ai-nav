数据库 迁移 AI：schema 对比与回滚

编程助手·更新于 2026-11-15·数据库 迁移 AI, DDL 转换, 数据 校验, 回滚 脚本, schema 对比 工具, 数据 迁移 回滚 演练

上个月把一套 SaaS 的库从 MySQL 5.7 迁到 PostgreSQL 16，18 张表、430 万行，客户只给 30 分钟停机窗口。我先让 Claude 读 SHOW CREATE TABLE 出转换稿，再拿 pg_dump 的 schema 做对比，最后把回滚脚本在影子库演练两遍。真实停机 25 分钟，演练时揪出 37 行金额差异。数据库 迁移 AI 能省的是体力，判断还得自己做。

schema 对比：AI 出稿，diff 兜底

步骤固定三步：1 用 mysqldump --no-data 导源库 DDL，用 pg_dump --schema-only 导目标库；2 两份 DDL 加目标版本贴给模型，要它输出“表、字段、差异、风险”四列表格；3 逐条复核。18 张表模型给出 63 处变更，我补了 11 处：外键删除策略 4 处、触发器 2 处、默认值 3 处、字符集 2 处。它最容易漏的是 TINYINT(1) 的布尔语义、DATETIME 的时区、索引前缀长度，还有把 MySQL 的 ENUM 直接映成 text 却没加 CHECK。存储过程和视图它基本不碰，两个视图是我手写改的。数据库 迁移 AI 在类型映射上给的是初稿，pgloader 自带的映射规则可以用来交叉验证。避坑一：它偶尔编出 PG 里不存在的函数，比如把 DATE_FORMAT 直译成 date_format，实际要写 to_char，跑之前先在空库执行一遍。schema 对比 工具 选哪种都行，最后以能在目标库跑通为准。

数据搬运：分批、校验、编码

数据用 pgloader 直连搬，或者 mysqldump 加转换脚本，按主键区间分页，每批 5000 行、每 1000 行 commit 一次，避免长事务把 WAL 撑大。编码最容易炸：导出加 --default-character-set=utf8mb4，否则表情符号和生僻字直接报 invalid byte sequence for encoding UTF8。校验做四层：行数、金额 SUM、按日 GROUP BY、每表抽 1000 行算 MD5。430 万行搬了 38 分钟，就是这层校验揪出 37 行订单金额差一分，原因是脚本把 decimal 当 float 处理。大字段走 COPY 的 CSV 模式，比逐行 INSERT 快三倍左右。搬完把自增序列 setval 到当前最大值，不然新插入立刻主键冲突。数据库 迁移 AI 生成校验 SQL 很顺手，但阈值和口径要自己定。

回滚：先演练，再切流量

回滚三条：迁移前全量备份并记下 binlog 位点；配一份反向脚本，Liquibase 的 rollback 或者手写；在影子库完整演练并计时。第一次演练回滚 41 分钟，超了窗口，第二次关掉索引重建、并行恢复，压到 18 分钟。切流量时先只读十分钟，确认报表和下单正常再开放写；旧库保留七天只读。数据 迁移 回滚 演练 的结论要写进操作单：谁在几分钟内拍板回退。AI 在这里只做两件事，生成校验 SQL 和解释报错，别把回滚脚本直接丢给它执行。演练记录留档，回滚命令提前写成脚本贴进操作单。避坑二：DROP 顺序先子表后父表，回滚前别删旧库，序列和触发器要跟表一起回滚。

总结

数据库 迁移 AI 的流程是 schema 对比、数据搬运、四层校验、回滚演练，每个环节都留人工复核。schema 对比 工具 决定初期少踩多少类型坑，数据 迁移 回滚 演练 决定出事时能不能在窗口内退回去。430 万行这次 25 分钟切完，靠的不是模型多聪明，是回滚先跑过两遍。
