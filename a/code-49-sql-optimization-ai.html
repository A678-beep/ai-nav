SQL 优化 AI：执行计划、索引与改写

编程助手·更新于 2026-11-15·SQL 优化 AI, 慢查询 定位, 执行计划 解读, 索引 优化, SQL 改写, 慢 SQL 如何 定位, 执行计划 解读 方法

上季度接一个 SaaS 后台，客户列表页翻到第 500 页要 11 秒，DBA 的第一反应是加机器。我把 3 天慢日志、两张表结构、执行计划整理成三段贴给模型，两轮锁定 3 条慢查询：一条深分页、一条缺索引、一条统计信息过期。改完 P99 从 3.8 秒到 210 毫秒，实例规格没动。SQL 优化 AI 有用的前提，是你把执行计划原样摊开给它看，而不是只发一句“这条查询很慢”。

先排优先级：慢日志按总耗时聚合

慢日志开 long_query_time=1，跑 3 天，用 pt-query-digest 聚合出 2.1 万条记录、380 条不同 SQL。让模型按总耗时占比乘频次排序，而不是只看单条最慢：单条 8 秒一天跑 2 次的，优先级低于单条 400 毫秒一天跑 5 万次的。前 3 条占 68% 总耗时，修这 3 条就够。按 SQL 指纹分组时注意参数化，别把 500 个不同参数当成 500 条语句。喂料固定五块：慢日志摘要、SHOW CREATE TABLE、SHOW INDEX、EXPLAIN 输出、数据分布（status 只有 4 个枚举值）。避坑一：只发慢查询不发表结构，模型会假设字段都有索引，建议全是空话；避坑二：把 200MB 原始慢日志整段贴上，上下文被截断，它只看到最后几条。慢 SQL 如何 定位 的答案在聚合，不在单条。

执行计划看三列，加实际行数

执行计划 解读 方法 就三步：type 是不是 ALL 或 index，rows 是不是接近表行数，Extra 有没有 Using temporary 和 Using filesort。MySQL 8.0.18 起用 EXPLAIN ANALYZE 看 actual rows 和 loops，估算和实测差 5 倍以上，统计信息八成过期，先 ANALYZE TABLE。统计信息过期那条，EXPLAIN 估 8 万行、实测 120 万行，ANALYZE 后从 1.1 秒到 240 毫秒。案例：一条 type=ALL、rows=940 万、filtered=10%、Extra 是 Using temporary 加 Using filesort 的查询，模型第一版建议给 created_at 建单列索引，可 status 只有 4 个值，选择度不够；改成联合索引 (status, created_at) 后 type 变 range、rows 降到 8 万，3.9 秒到 380 毫秒。第二处是 order_items 缺 (order_id) 索引，换成覆盖索引 (order_id, sku_id, qty)，回表消失，到 90 毫秒。避坑三：让它用 FORCE INDEX 硬顶，指标好看，换个月份就崩；避坑四：不看写放大，这张订单表写入 TPS 从 1200 掉到 980。SQL 优化 AI 给的索引要先在从库验证，别直接上主库。

改写只做四类，行数必须核对

我让模型只做四类改写，每类标风险：深分页改延迟关联，先查 id 再回表，LIMIT 500000,20 从 3.9 秒到 210 毫秒；大 IN 列表拆 UNION ALL 或写临时表；SELECT 全字段收窄到 8 个字段；相关子查询改派生表加窗口函数。每条改写都要重跑 EXPLAIN 对照 rows，再用 COUNT 核对行数。模型把 LEFT JOIN 改成 INNER JOIN 的那种“优化”我遇到两次，报表少了 300 多行，数字对不上比慢更严重。改写也别动业务语义：OR 拆 UNION 时漏掉去重，同一订单会被统计两次。索引最后收一次：3 个索引里删掉 1 个重复前缀的，净增 2 个。

总结

闭环四步：慢日志聚合排优先级、执行计划取证、索引或改写、核对行数和写放大。慢查询从每天 2100 条降到 60 条，P99 3.8 秒到 210 毫秒，实例规格没加。SQL 优化 AI 只是加速器：慢 SQL 如何 定位 靠日志排序，执行计划 解读 方法 靠 type、rows、Extra 三列，这两步人得自己会，它给的建议才敢上线。
