代码 文档 生成：从注释规范到 CI 流水线

编程助手·更新于 2026-11-15·代码 文档 生成, 注释 规范, Sphinx, 文档 覆盖率, CI 校验, 代码 文档 自动 生成, 代码 文档 覆盖率

接手一个十二万行的 Python 老仓库，四百八十个公共函数，新人问得最多的是"这个参数到底传什么"。文档不是没有，散在 wiki、注释和老人口头里，搜不到也算不上；四百八十个函数里只有一百三十个写了 docstring，中英文混排，参数段大半空着。我用六周把 代码 文档 生成 做成一条流水线：注释改成可解析格式、生成器出站点、CI 卡覆盖率，新人上手提问从每周二十个降到六个。

注释规范：能被解析才谈得上生成

第一步统一成 Google 风格 docstring，四条硬规则：首行一句话说清做什么，七十二字符以内；参数、返回、异常三段齐全，类型只写在 type hint 里，docstring 不重复写，写了迟早和代码打架；单位写进描述，比如"金额，单位分"；给一段能跑的示例，后面接 doctest。Python 走 Sphinx 加 napoleon，前端走 TSDoc。避坑一：中文全角冒号和括号会让 napoleon 解析错位，参数表整段不渲染；避坑二：只写做什么不写边界，新人照样踩空值。评审规则也跟着定：新增公共函数缺参数和异常两段直接退回，行内注释只复述代码的同样退回。这层是 代码 文档 生成 的地基，地基歪了后面全是返工。

工具选型：够用就好，别追全量

Python 侧我用 Sphinx 7.3 加 autodoc，构建带 -W 把警告当错误；想轻量就 mkdocs-material 加 mkdocstrings，四十九页三分钟构建完，团队更愿意用。TypeScript 用 TypeDoc，C++ 才上 Doxygen。配置里两个开关别乱开：undoc-members 会把没注释的私有方法全翻出来，页面全是空条目；nitpicky 打开后交叉引用写错一个就报错，前期痛后期香。中文搜索要单独配，默认按单字切，"代码 文档 自动 生成"这种词组搜不到，加 separator 才整词命中。站点按模块做三级导航，函数页放签名、参数表、示例和调用位置，搜到就能跳源码行。

CI 闸门与覆盖率

代码 文档 生成 的关键不是生成，是守。PR 里跑 make docs，sphinx-build 带 -W 失败就阻断；每周跑 linkcheck，失效链接和内网地址会被揪出来。代码 文档 覆盖率 用 interrogate 卡，--fail-under 85，只卡新增文件，全量开闸 CI 会永远红。六周覆盖率从 28% 到 92%，构建三分四十秒。AI 可以补，但只让它补示例和边界说明，参数含义人工确认，它编的解释比没有更坏。避坑三：拿 docstring 行数冲 KPI，一定催生空壳；避坑四：把生成的 build 目录提交进仓库，每次 diff 上千行。

总结

现在四步固定：注释按可解析格式写、生成器出站、CI 卡覆盖率、AI 只补示例，流水线每周顺手更新一次版本号。代码 文档 自动 生成 跑进每次合并以后，省下的不是写文档的时间，是新人反复问同一个问题的时间。代码 文档 覆盖率 到 92% 以后我把它调成只卡新增，存量按季度清。两条底线：别追求全量生成，别让机器替你解释业务。
